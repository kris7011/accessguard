## Hardening before milestone 2

Carried out on the same branch after commit `e21c8ff`. Each problem was reproduced with a
failing test before it was fixed.

### H1: false PASS when a denial response still contained protected data (fixed)

**Problem.** `evaluate_item` and `evaluate_list` only looked for protected content in 2xx
responses. A 401/403/404 whose body echoed the resource (e.g. `{"error": "forbidden",
"requested": {...}}`) became PASS, and the run could be reported as `checks_passed`.

**Reproduction.** New lab flaw `denial-body-leak` (403 with the document in the error body) and
edge route `/edge/leaky-denial/{id}`. With the e21c8ff engine the profile scanned as
`checks_passed, PASS 56`, exit 0 (a false green). After the fix: `findings, PASS 42 / FAIL 14`,
exit 1, exactly the hand-written ground truth.

**Fix** (`domain/evaluation.py`, ADR 0002 amendment). Protected content is matched for every
status code before the status is interpreted. For an actor the policy does not grant, all
protected values → FAIL (`unauthorized_access`), some → SUSPECTED, regardless of status and
session state. Only a denial without protected content is PASS. For a granted actor, a denial
status whose body contains the granted content is INCONCLUSIVE (contradictory); a denial without
content stays FAIL (`expected_access_denied`). Error responses without a leak (5xx, 429, 3xx) stay
INCONCLUSIVE: neither a finding nor a pass. The same applies to listings. Evidence still lists
field names only.

**Tests that failed before and pass after:**
`tests/unit/test_evaluation_status_matrix.py` (item and list × 200/401/403/404/500 ×
full/partial/no match, shared grant as negative control: 29 failing sub-cases and 1 error before
the fix), `test_edge_cases.py::test_ambiguous_responses_for_cross_tenant_actor` (`leaky-denial`
was PASS) and `test_lab_scans.py::test_each_flaw_in_isolation` (`denial-body-leak`: 14 false
negatives).

### H2: verification commands could hide failures (fixed)

**Problem.** The CI step `git ls-files -z | xargs -0 detect-secrets-hook ...` ran without
`pipefail` (no explicit `shell:`), so a failure of `git ls-files` was hidden. The M1 verification
run itself piped test output through `tail`; success was judged from the printed "OK", not from
the exit code.

**Fix.** `ops/verify.sh` (bash, `set -uo pipefail`) and `ops/verify.ps1` (Windows PowerShell 5.1
and PowerShell 7) run each step as a single Python invocation, write output to a log file, take the
exit code from the command itself, run all requested steps and exit with the first failing step's
original code. A missing interpreter fails the run. The CI pipeline was replaced by
`ops/ci/secret_scan.py`; CI sets `defaults.run.shell: bash` and calls the same scripts.

**Negative control.** `bash ops/verify.sh selftest-pass selftest-fail selftest-pass` → exit 3
with `FAILED selftest-fail (exit 3)`; `verify.ps1 -Steps selftest-fail` → exit 3. Automated in
`tests/e2e/test_verify_scripts.py`, which also demonstrates that `cmd | tail` returns 0 without
`pipefail`.

### H3: time limits and cancellation did not cover in-flight requests (fixed)

**Problem.** The run deadline and the stop signal were checked only *before* a request. The socket
timeout applied per read, so a slow-drip body (one byte per 0.1 s) took 3 s despite a 0.5 s
timeout; a 1.5 s response delayed both the deadline and cancellation; pacing slept
uninterruptibly; Ctrl+C aborted the CLI without a report.

**Fix.**

- `adapters/http_transport.py`: the request timeout is a **total** wall-clock limit. Reads run on
  a socket with 50 ms timeout slices that re-check the deadline and the cancel event before every
  read, so no cross-thread socket operation is needed. (A watchdog thread that shut the socket down
  was tried first; it did not interrupt a blocked `recv` on Windows.) The response and the
  connection are always closed; a socket that stayed open after an aborted request was found and
  fixed.
- `application/gate.py`: `acquire()` returns a `RequestLimit` (remaining run time and the stop
  event); pacing waits on the stop event.
- `application/runner.py`: a transport error caused by the deadline or the stop signal is an
  interruption. The in-flight check becomes SKIPPED ("Interrupted while in progress, no verdict"),
  later checks SKIPPED ("Not executed"); completed results are kept.
- `entrypoints/interrupt.py` and the lab CLI: SIGINT, SIGTERM and Ctrl+Break set the stop event,
  the scan runs in a worker thread, the partial report is written, the lab is shut down by its
  context manager and the process exits with **130**. New options `--min-interval` and
  `--max-duration`.
- Reports: `run.completed`, `status.complete` and an interruption note in `status.meaning`.

**Tests that failed before and pass after:** `tests/integration/test_time_limits.py` (slow-drip
total limit, run deadline bounding a slow in-flight request, cancellation of an in-flight request,
interruptible pacing; `test_aborted_request_releases_its_socket` fails with the socket still open
when the response is not closed) and `tests/e2e/test_cancellation.py` (real subprocess, Ctrl+Break
on Windows / SIGINT on POSIX: exit 130, partial report with PASS and SKIPPED results).

**Mutation check.** Five mutants of the fixes (leak precedence for items and for lists, slice
loop, deadline conversion in the runner, interruptible pacing) were all detected by the suite.

### H4: false PASS when a denial body could not be analysed (fixed)

**Problem.** The engine only reads JSON. A 401/403/404 whose body was HTML, plain text, invalid
JSON or JSON behind a non-JSON Content-Type yielded no values to compare, so the response was
treated like an empty denial and became PASS, even when it carried the protected data.

**Reproduction.** Six new lab edge routes answer a cross-tenant read with 403 and a body the
engine cannot parse: `html-denial`, `text-denial`, `invalid-json-denial`, `html-as-json-denial`,
`mislabelled-json-denial` (all containing the synthetic title and canary of `acme-doc`) and
`empty-denial` (zero bytes). With the 46c6ec3 engine, a scan of these routes was reported as
`checks_passed`: all five leaking routes were PASS. In `tests/unit/test_unanalysable_responses.py`,
36 item sub-cases (6 body formats × 401/403/404 × leak) and 18 listing sub-cases were PASS; 78
sub-case assertions failed in total.

**Fix.**

- `domain/observation.py`: `BodyFormat` (`json`, `empty`, `unsupported`, `invalid_json`) replaces
  the `is_json` flag (now a derived property), so "no body" and "body not read" are distinct.
- `adapters/http_transport.py`: `decode_observation` classifies every body by the declared
  Content-Type; bodies are never sniffed.
- `domain/evaluation.py`: a denial status counts as PASS only with a `json` or `empty` body. An
  unanalysable body gives INCONCLUSIVE with the reason "leaked protected content cannot be ruled
  out", for items and listings alike; 2xx with such a body is INCONCLUSIVE for both expectations.
  Leak precedence for parsed JSON is unchanged. A granted actor that is denied stays FAIL
  (`expected_access_denied`); the reason notes that the body was not analysed. The owner baseline
  names the format problem. Reasons contain only the body size, never content.
- Reports: a new `not_tested` entry explains that non-JSON and invalid-JSON bodies are not analysed.

**When an empty denial counts as PASS.** A 401 (with a verified session or for the anonymous
actor), 403 or 404 whose body is exactly zero bytes, whatever its Content-Type, because no
protected value can be present. A whitespace-only body declared as JSON is `invalid_json` and
therefore INCONCLUSIVE.

**After.** The same scan: `incomplete`, five INCONCLUSIVE, `empty-denial` PASS, no findings; the
report JSON and HTML contain neither the title nor the canary
(`test_edge_cases.py::test_unanalysable_denials_are_never_pass`). All sub-cases above pass.

**Mutation check.** Six mutants (unanalysable detection disabled; the item-denial, list-denial and
list-success branches removed; the decoder mapping unsupported or invalid JSON to empty) were all
detected by the new tests.

**Limitation kept on purpose.** A leak inside an HTML or plain-text body is not reported as a
finding; it is INCONCLUSIVE and needs manual review (ADR 0002, second amendment). Targets that
answer denials with HTML error pages therefore get lower conclusive coverage.

## Not done or not verified

- GitHub Actions has not run (nothing pushed). Python 3.11 and Ubuntu are in the CI matrix but
  unverified.
- No real language model was run; the Ollama adapter is verified with mocks only.
- No agent loop, ML, external targets, HTTPS, write checks, pagination, UI or database (later
  milestones, by design).
- Time limits are enforced with 50 ms granularity during reads. TCP connect and request sending are
  bounded by the remaining time but cannot be cancelled mid-call (loopback only in M1).
- A second signal does not force-quit; the run stops at the next 50 ms slice or pacing check.
- Leak detection still requires exact JSON string values; leaks in HTML or other non-JSON error
  bodies are not reported as findings. Since H4 such responses are INCONCLUSIVE instead of PASS.
