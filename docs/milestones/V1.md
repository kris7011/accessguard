# V1 — first commercial version (paid beta)

Status: **11 of 12 packages accepted; operations (10) is implemented but blocked on a server and external accounts; billing (6) accepted for test mode against a Stripe sandbox and AI assistants (7) for the synthetic scenarios with one real-model run, both on 2026-10-30** (branch `feature/v1-commercial-beta`, started 2026-10-29 from `b94f5b7`).
This file is the plan and the acceptance record. Each criterion is marked when verified, with
the command or test that verified it.

## Starting point

- The engine (M1) and the bounded agent (M2) are complete and verified (285 tests, 283 passed,
  2 opt-in skipped; gates green at `b94f5b7`).
- M2 result, kept as is: **no demonstrated prioritisation advantage** of the real model over
  simple rules. The benchmark is not rerun. The product therefore uses complete deterministic
  coverage as its scan strategy, and AI is used where it reduces customer work (setup drafts,
  explanations, fix suggestions), never for verdicts, scope or budgets.
- The engine is loopback-only, Bearer-only and has no product shell (no accounts, UI, billing).

## Scope of V1 (what is in, what is out)

In: self-serve web control plane, local runner, a separate synthetic integration app, scan
lifecycle with approval, findings with triage and retest, deterministic fix guidance, two
bounded AI assistants, ML data and training foundation (activation gated by evaluation),
Stripe test-mode billing, marketing and onboarding pages, deployment/ops files and docs.

Out (explicitly, for later versions): write-operation tests, crawling or endpoint discovery
on live targets, SSO/SAML, automatic code changes in customer repositories, hosted scanning
of customer targets from our servers, YAML OpenAPI import, live payments.

## Key decisions (ADRs 0009-0013)

1. **Local runner (pull model).** The control plane stores policy and scope but never
   credentials and never contacts customer targets. A runner in the customer's environment
   claims approved jobs, reads credentials locally, scans, scrubs and uploads a report that
   contains no credentials and no response values. The job's origin must also be on the
   runner's local allowlist, so a compromised control plane cannot redirect scans.
2. **Django 5.2 LTS, server-rendered.** Accounts, sessions, CSRF, forms, migrations and admin
   are built in; no separate SPA build. SQLite locally, PostgreSQL in production.
3. **Stripe Checkout + Customer Portal**, signature-verified idempotent webhooks, entitlements
   derived from subscription state.
4. **AI assistants with narrow contracts**: setup draft from an OpenAPI document and finding
   explanations. Schema-validated output, user approval before anything changes, deterministic
   alternatives always available, provider behind a port (Anthropic, local Ollama, none).
5. **ML foundation, not an active model**: verified labels with provenance, versioned features
   and datasets, grouped splits by application, baselines, registry with promote/rollback.
   A learned ranker is activated only if it beats the baselines on held-out applications.

## Acceptance record (updated 2026-11-02 with the real-model run of 2026-10-30)

a written or mocked part can never read as done:

- **Implemented**: the code or document exists in this branch.
- **Verified locally**: exercised for real on the development machine (Windows 11, CPython
  3.13.13 unless stated) by tests or a recorded run. Mocks and fake providers do not count.
- **Blocked externally**: the part that cannot be verified without an account, key, server or
  approval the owner has to provide. "—" means nothing is blocked.

blocked. Overall: **11 of 12 accepted; 10 implemented but not accepted.** Billing (6) is
accepted for test mode only; live payments are outside V1. AI assistants (7) are accepted

**Why the local AI model was not run.** Ollama 0.40.11 and `qwen3:4b-instruct-2507-q4_K_M`
are installed, and setup B ran in M2. The assistants' provider uses `num_ctx` 16384 (twice
M2's 8192), so it would need more than the 4.6-4.8 GB `llama-server` held in M2. On
2026-10-30 the machine had 1.2-3.5 GB free commit memory. It also crashed twice that morning
with bugcheck `0x116` (`VIDEO_TDR_FAILURE`, parameter `0xC000009A` =
`STATUS_INSUFFICIENT_RESOURCES`) while Docker's VM ran. A GPU-heavy model run under that
memory pressure risked a third crash, so it was not started.

### What a customer can do today (locally)

Sign up; run the demo scan against the synthetic API; read findings with evidence and fix
guidance; "deploy" the fixed demo and retest to verified resolution; create a project for
their own test environment with forms (or import endpoints from OpenAPI); create a runner
token; run the runner next to their environment; approve, follow, stop and read scans;
triage and retest findings; invite colleagues with roles; see plan limits; delete their
organisation. Upgrading works only once Stripe keys are configured.
