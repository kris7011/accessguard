**Delivery status: M2 implementation with mock and contract verification, plus one passed
real-model smoke test.** The agent loop, its limits and the Ollama adapter are verified with a
scripted test adapter, mocked model clients and a local fake Ollama HTTP server. On 2026-10-27 a

## Design summary

See [ADR 0007](../adr/0007-bounded-adaptive-agent.md) (agent) and
[ADR 0008](../adr/0008-selection-strategy-evaluation.md) (evaluation).

```text
            ┌──────────── ModelView (aliases, enums, ints) ────────────┐
            │                                                          ▼
CheckRunner.preflight ─► AgentLoop ──ModelRequest──► ModelClient (Ollama | scripted)
                            ▲  │                                       │
                            │  └◄── parse_action (strict contract) ◄───┘ ModelReply (untrusted)
                            │         run_check(alias) | stop | rejected
                            ▼
                  CheckRunner.execute(approved check) ──► RequestGate ──► ScopedHttpClient
                  (deterministic verdict)                 (budget, deadline, stop; also
                            │                              bounds every model call)
                            ▼
              CheckRunner.finish (retests) ─► build_report (schema 1.2, run.agent)
```

### Information basis

The model sees opaque aliases plus:

- the expected access (`allow`/`deny`);
- the actor-resource relation (owner, same tenant, shared grant, cross tenant, anonymous);
- the owner tenant, tenant and role aliases, and session state;
- previous outcomes (outcome, finding type, HTTP status);
- the budget.

It never sees names, paths, bodies, the answer key or flaw profiles.

That is enough for meaningful priors and follow-up. Before a first finding, however, it does
not distinguish structurally similar checks. In addition:

- list checks are not linked to tenants or categories;
- roles carry no privilege information.

The structure was deliberately left unchanged, so that the first real model is measured on
`agent-v1`. Details and the proposed `agent-v2` ablation:
[evaluation.md](../evaluation.md#information-basis-of-the-agent).

**Insufficient basis** (as of 2026-10-26; still true after the 2026-10-27 smoke test and the

A **reproduced finding** (a FAIL whose separate retest gave the same result) and a **correct
classification** (the outcome the hand-written answer key expects) are separate properties.
Here all 3 FAILs have both, and the 9 PASSes are correctly classified. Neither says anything
about the 44 checks that were never executed.

**Selection (observation, not a quality claim):** the model chose policy positions 25-37 in
order. It started at the first `deny`/`cross_tenant` check after the shared-grant block and
skipped position 28 (`acme-invoice@acme-admin`, an `allow`/`owner` check). The smoke test's
first choices were different (positions 53-55). Its state also differed, because the
model-call budget was 3 instead of 200, so this does not show non-determinism. Twelve choices
are no basis for judging prioritisation.

### Cause: the llama-server host prompt cache (Ollama runtime, not AccessGuard code)

Ollama 0.40.11 runs the model in a `llama-server` child process. Its log states:

- "prompt cache is enabled, size limit: 8192 MiB" and "use `--cache-ram 0` to disable the
  prompt cache";
- "idle slots will be saved to prompt cache upon starting a new task".

Before every new call it saved the previous prompt's full state (419-470 MiB) in host memory.
At the stop the log shows "cache state: 12 prompts, 5263.751 MiB", which matches the about
5.5 GB of commit growth after the model load. The same log also shows
"disabling mmap for llama-server load by default ... reason=windows_cuda", so the weights are
private memory rather than a file mapping.

The cache gave this workload almost nothing: each new prompt of about 3.1k tokens reused only
185-186 cached tokens. The state changes near its start (for example the budget counters), so
most of every prompt is evaluated again anyway.

How AccessGuard was ruled out:

- The same unchanged full test was run against the project's fake Ollama server (no model; a
  scratch diagnostic, not committed). The test process's private memory grew from 18.7 MB to
  21.8 MB over 56 calls, about 0.03 MB per call.
- The private memory of the other large programs (Chrome, VS Code) was the same before and
  after the run.
- After the stop, committed memory fell to 19.97 GB, below its value before the run.

No AccessGuard defect was found, so no code, assertion or limit was changed. The failure
handling worked as designed: the agent reported an explicit failed status, kept its completed
results and marked the unfinished checks SKIPPED, with coverage 12/56 rather than full.

### What blocks the full test on this machine

- **Expected need (an estimate, not measured to the end):** about 4.7 GB of commit for the
  model load, plus up to 8 GB of prompt cache (about 19 prompts at its 8192 MiB limit).
- **Available:** about 4.5 GB of free commit with the owner's programs open, and 7.3 GB of
  physical RAM in total.
- **Already at 12 calls:** physical RAM was exhausted and call latency had tripled.

Options for the owner. Each one changes the setup compared with the smoke test, so none was
tried here:

1. **Disable or limit the prompt cache** (preferred, since it brings almost no reuse here).
   Ollama's documented server settings (`ollama serve --help`, 0.40.11) do not expose it.
   llama.cpp's server reads `LLAMA_ARG_*` environment variables for its options. Whether
   Ollama passes such a variable on to its `llama-server` child is not documented and was not
   verified. That needs checking against the llama.cpp documentation, then a short smoke run
   with memory monitoring.
2. **Free memory by closing programs yourself before the run.** On its own this is probably
   not enough, given the 8 GB cache limit.
3. A larger fixed page file makes the run slower (paging) but does not make it safer. It is
   not recommended.
4. Make the stable part of the model state come first, so that the prompt prefix can be
   reused. This only changes speed, but it changes the model input. It is a candidate for
   `agent-v2`, not for `agent-v1`, which is being measured.

The partial reports, the server log, the memory samples and the scratch scripts are kept
locally in `reports/real-model-full-test-2026-10-27/` (git-ignored, not committed).
