## Design summary

See [ADR 0007](../adr/0007-bounded-adaptive-agent.md) (agent) and
[ADR 0008](../adr/0008-selection-strategy-evaluation.md) (evaluation).

```text
            ┌──────────── ModelView (aliases, enums, ints) ────────────┐
            │                                                          ▼
CheckRunner.preflight ─► AgentLoop ──ModelRequest──► ModelClient (Ollama | scripted)
                            ▲  │                                       │
                            │  └◄── parse_action (strict contract) ◄───┘ ModelReply (untrusted)
                            │         run_check(alias) | stop | rejected
                            ▼
                  CheckRunner.execute(approved check) ──► RequestGate ──► ScopedHttpClient
                  (deterministic verdict)                 (budget, deadline, stop; also
                            │                              bounds every model call)
                            ▼
              CheckRunner.finish (retests) ─► build_report (schema 1.2, run.agent)
```

## Evaluation outcome (scripted adapter)

The scripted `follow-up` heuristic matched the deterministic baseline at every budget. It gave
no advantage. Seeded random orders found the first expected finding earlier on these fixtures,
because the flawed resources are declared late in each policy. At full budget, every strategy
found every expected finding, with 0 false positives. Details and caveats are in
[evaluation.md](../evaluation.md).

  2026-10-26) and is contract-tested against a fake server only.
- GitHub Actions has not run (nothing pushed). Python 3.11, Linux and macOS are not verified
  locally.
- The scripted adapter is a deterministic heuristic, so its evaluation results describe the
  mechanics, not AI.
- Only 4 small synthetic fixtures. Results are sensitive to declaration order and say nothing
  about real applications.
- One model call per check; the state grows linearly with the number of checks.
- Retests run after all selected checks, so a run that exhausts its HTTP budget leaves its
  findings unconfirmed (`not_retested`), whatever the strategy. Reserving budget for retests is
  a candidate change. It needs its own decision, because it changes every strategy.

## Real-model readiness review (2026-10-26, second session)

Starting point: commit `c0abc42`, clean working tree. No model was installed or downloaded,
no paid API was used, and no external system was scanned.

### Do the opt-in test and the evaluation exercise the adaptive agent?

**Yes.** Both go through the adaptive agent loop (`AgentLoop`), not the earlier reorder
planner (`OllamaPlanner`, which only `accessguard-lab scan --model` uses):

- `tests/e2e/test_real_model.py` builds an `AgentStrategy` around `OllamaModelClient`.
- `accessguard_eval run --model ollama:NAME` runs `run_agent_scan`
  (`harness.run_once`).

**Gaps found and fixed:**

| Gap | Consequence | Fix |
| --- | --- | --- |
| The opt-in test asserted only `status != model_failed` | A model whose every reply was invalid (`invalid_replies_exhausted`, 0 checks executed) would have **passed** | The test now fails on every failed status and requires at least one accepted `run_check`. A run against the fake Ollama server with always-invalid replies confirms that both tests now fail; with valid replies they pass |
| No small, bounded real-model test | The first contact with a model would be a run of up to 30 minutes | New `test_smoke_a_few_bounded_model_calls`: 3 model calls, 120 s per call, 600 s per run |
| The evaluation ran the agent once per budget | No measure of run-to-run variation of a real model | `--agent-repeats N`. Every repetition is scored and averaged, never selected; `distinct_selection_orders` shows stability |
| Fixed 300 s run deadline | A real model would probably hit it at full budget | `--max-run-seconds`, the same for every strategy (validated before any run) |
| Missing provider metadata was simply absent | It could not be told apart from "not recorded" | `ModelDescriptor.provenance_keys`. The evaluation lists every declared key and writes `"unknown"` for a key that was not reported; it also writes the metadata errors |
| No distinction between candidate and confirmed findings | — | `confirmed_true_positives` (FAIL plus reproducing retest), `model_seconds` and `agent_statuses` per summary row |

The scripted `deny-first` adapter was also added. It is a non-AI reference showing what the
structural state alone allows.

### Information basis

The model sees opaque aliases plus:

- the expected access (`allow`/`deny`);
- the actor-resource relation (owner, same tenant, shared grant, cross tenant, anonymous);
- the owner tenant, tenant and role aliases, and session state;
- previous outcomes (outcome, finding type, HTTP status);
- the budget.

It never sees names, paths, bodies, the answer key or flaw profiles.

That is enough for meaningful priors and follow-up. Before a first finding, however, it does
not distinguish structurally similar checks. In addition:

- list checks are not linked to tenants or categories;
- roles carry no privilege information.

The structure was deliberately left unchanged, so that the first real model is measured on
`agent-v1`. Details and the proposed `agent-v2` ablation:
[evaluation.md](../evaluation.md#information-basis-of-the-agent).

Sources were checked on 2026-10-26:

- [Ollama Windows docs](https://docs.ollama.com/windows);
- [Ollama model page](https://ollama.com/library/qwen3:4b-instruct-2507-q4_K_M);
- the [model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) and its `config.json`.

Why this model:

- **License: Apache 2.0** (model card and Ollama page). It is permissive and has no usage
  thresholds, which suits a product meant to be sold.
- **Non-thinking only** (model card: "supports only non-thinking mode and does not generate
  `<think></think>` blocks"). The agent allows only 64 output tokens per reply, which leaves no
  room for reasoning tokens.
- Its 2.5 GB Q4_K_M build is about the largest that this GPU can plausibly hold at the
  required context (see the VRAM estimate below).

**Uncertainty:** the Ollama page lists a "thinking" capability for the qwen3 family. The
smoke test will show whether the replies are clean JSON.

Requirements and expected footprint:

| Item | Official / measured | Fits? |
| --- | --- | --- |
| Windows | 10 22H2 or newer, Home or Pro (Ollama docs) | yes |
| NVIDIA driver | 551.61 or newer (Ollama docs); installed 610.62 | yes |
| Disk | at least 4 GB for the Ollama install (docs) plus 2.5 GB download (Ollama page) ≈ 6.5 GB of 17.7 GB free | yes |
| VRAM | My estimate, not official: about 2.5 GB weights plus f16 KV cache at `num_ctx` 8192 (36 layers × 8 KV heads × 128 × 2 × 2 bytes = 144 KiB per token, about 1.1 GiB) plus compute buffers (a few hundred MB, uncertain) ≈ 3.8-4.2 GB, against about 3.5 GB free | **probably not fully**: expect Ollama to put some layers on the CPU. That is slower, but it should work |
| RAM | Not stated for this model by Ollama. CPU-resident layers and the server use system RAM | **tight**: close other programs during runs. Paging is a risk |
| Context | Largest state: about 14.2k characters (dev lab, all checks done). Measured in characters; about 4-6k tokens is my estimate, not tokenizer-measured. `num_ctx` 8192 suffices; 4096 would risk truncation | yes, at 8192 |

Expected run time is **uncertain**, probably several seconds per call, because every call
resends the whole state. A full evaluation with 3 repetitions needs roughly 800 model calls,
so expect about 1-3 hours. Run the subset first.

If the CPU split proves too slow, a smaller model would fit the GPU better. Its license must
then be checked separately.

Installing Ollama (at least 4 GB) and downloading the model (2.5 GB) is an owner decision. It
was not done here.

### Conclusion

**Insufficient basis.** No real model has run, so there is no evidence for or against an AI
advantage. The scripted references show no advantage over seeded random order on these
fixtures.

A correctly completed real-model run would prove the integration (contract, limits,
provenance and deterministic verdicts). It would not prove the product's security or its
commercial value.
