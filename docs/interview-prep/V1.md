# Interview preparation: V1 commercial beta

How V1 was built: the code, tests and documents were written with AI assistance (Claude Code)
from the owner's requirements; the owner decides, reviews and must be able to explain them.
Be explicit about that in interviews: "I specified and reviewed it, and I can walk you
through every decision", not "I typed every line".

## Three levels of explanation

**Non-technical.** Many software companies host data for many customers in one system. A
single missing check can let one customer see another's data. AccessGuard lets a team write
down who may see what, then tests every combination automatically, shows proof for every
problem, and checks again after it is fixed. The testing program runs inside the customer's
own network, so their passwords never leave it.

**Developer.** A Django control plane stores each project's configuration as a scan spec (the
same JSON the runner executes). A person approves the scope; the spec is frozen and hashed.
A stdlib-only runner polls a small bearer-token API, refuses origins that are not on its
local allowlist, loads test credentials locally and runs the engine: owner baseline first,
then every actor against every record and list, protected values matched in the response,
failures retested. The report (no credentials or response values) is uploaded, validated
against the approved checks and turned into findings with stable fingerprints; a later PASS
of the same check resolves a finding as verified, a reappearance reopens it.

**Senior / architectural.** The main decision is a pull-based runner: it removes the SSRF
surface and the credential vault from the hosted service and gives two independent
authorisations (approval in the app, allowlist on the runner), at the cost of an installed
component. One validation source (the engine's parser) backs the UI, the CLI and the runner.
Verdicts are deterministic and presentation has one rule for "green". AI is bounded to
drafts with schema validation and consent; the ML pipeline exists with a promotion gate that
currently refuses activation, which is the honest result with synthetic data only.

## Five interview questions with example answers

1. **Why a runner in the customer's environment instead of scanning from your servers?**
   Scanning needs test credentials and reads responses with customer data. If our servers did
   it, we would hold credentials for many companies and be able to reach arbitrary hosts, an
   SSRF platform. With the runner, our servers never connect to targets, credentials stay
   local, internal staging works without opening firewalls, and the runner's allowlist means
   even a compromised control plane cannot redirect scans (`check_spec_against_trust`).
   The trade-off is installation effort and needing the runner online.

2. **How do you guarantee one customer cannot see another's findings?**
   Every product model has an organisation; `tenancy.get_owned` filters by the current
   membership's organisation and answers 404 for anything else, so ids are not confirmed. Roles
   gate mutations. Runners only see their organisation's scans and only scans they claimed.
   It is tested route by route in `IsolationTests` and for the runner API.

3. **Why Django and server-rendered pages rather than FastAPI and React?**
   V1 needed accounts, sessions, CSRF, forms, migrations and an admin, built by one person.
   Django provides those; server-rendered pages keep a strict CSP without inline scripts and
   are easy to test with the test client. FastAPI + SPA would be better for a large public
   API or a highly interactive editor; I would revisit then (ADR 0010).

4. **How do you make payments reliable?**
   Plans change only through signature-verified webhooks. Each event id is stored with a
   unique constraint in the same transaction as its effect, so retries are no-ops. Stripe
   does not deliver in order and `created` has one-second resolution, so an event is only a
   signal: under a row lock the webhook fetches the subscription from Stripe and mirrors its
   current state, and ignores events of a subscription the organisation no longer follows.
   (A first version compared `created` timestamps; sandbox-driven regression tests showed
   that a late payment failure, an old subscription's events and same-second events could
   still apply stale state.) Upgrades use `pending_if_incomplete`, so a higher plan applies
   only once paid, and a grace period keeps only the plan already held. Card data never
   touches us (Checkout, the Customer Portal and hosted invoices).

5. **Where is the AI, and why not more?**
   The M2 evaluation showed no prioritisation advantage of a local model over simple rules, so
   scans run every check deterministically. AI drafts setup from OpenAPI (it can only pick
   extracted paths and fields) and explains findings (validated output, labelled draft). The
   learned ranker failed its pre-defined gate on synthetic data, so it is not active. I can
   show the numbers and the gate rather than claim self-improvement.

## Addendum (2026-10-30): verifying the release from the customer's side

What was done with AI assistance (Claude Code) in this session, and what you should be able
to explain yourself: the acceptance script, the four fixes below and the Docker run were
implemented and executed by the assistant; the decisions to keep the AI and Stripe items
marked "blocked" and not to run the local model on this laptop were made from the measured
facts recorded in `docs/milestones/V1.md`.

**Non-technical.** We installed the product the way a customer would, from the file we would
send them, on a clean setup, and went through sign-up, setup, a scan, a fix and a retest. That
found a bug no automated test had found, plus three problems in the server setup that would
have stopped backups from ever working.

**Developer.** `ops/dev/customer_acceptance.py` builds each POST from the rendered page,
including what a browser adds on its own (empty formset rows, the first option of an
unselected `<select>`). The runner comes from a venv with only the wheel installed, started
without `PYTHONPATH`, so the repository cannot leak into it. The compose stack was tested
with an override that changes only the env file and a loopback database port, so the real
`docker-compose.yml` was what ran.

**Senior.** Tests that post hand-built data verify the server's contract, not the product a
user operates; the gap here was the browser's implicit form semantics. Similarly, written
deployment files are a hypothesis until built: version skew (pg_dump 15 vs server 17), start
order without health dependencies, and a missing build-context filter are invisible to unit
tests. The status model now separates implemented, verified locally and blocked externally,
so mocks never count as verification.

**Questions and example answers.**

1. *Why did the rules page fail only in a browser?* The owner select had no blank choice. A
   browser submits the first option, so Django saw the empty extra row as changed
   (`has_changed()` compares with the initial `None`) and validated it as a half-filled
   record. The fix is a blank first choice; the test (`test_project_setup.py`) builds POST
   data from the rendered HTML with browser rules.
2. *Why move the images from bookworm to trixie instead of installing the PGDG client?*
   Debian 13 ships postgresql-client 17, which matches the server with no extra apt
   repository or signing key to maintain. The trade-off is a newer base; the rule to remember
   is that `pg_dump` must be at least the server's major version.
3. *How do you know the restore worked?* It went into a separate database, `migrate --check`
   was clean, and exact row counts for every model plus a digest over user e-mails, finding
   fingerprints and every report matched the source.
4. *Why not count the mocked Stripe and Anthropic tests as verified?* They prove our handling
   of messages we construct, not that the provider accepts our requests (a wrong parameter
   name, a beta header, a webhook configuration). Those need one real test-mode run.
5. *What would you do about `pip install accessguard` in the docs?* Remove it until we own the
   name: an unpublished name can be registered by anyone, and the instruction would install
   their package (dependency confusion). Customers get the wheel and its SHA-256.

## Addendum (2026-11-02): voiding the failed renewal after Stripe's final action

**Non-technical.** If a customer's card keeps failing, Stripe tries again for two weeks and
then ends the subscription. Before this change, the unpaid bill stayed open and could still
be paid for a plan that had already ended. Now AccessGuard cancels exactly that bill, tells
the customer on the billing page, and lets them subscribe again normally.

**Developer level.** Every handled webhook fetches the subscription's current state from
Stripe under a row lock (existing design). After the tenant check, `_void_failed_renewal`
(`billing/webhooks.py`) checks whether Stripe cancelled it with
`cancellation_details.reason == "payment_failed"`; if so, it reads the subscription's
`latest_invoice` and voids it only if it is `open`, a `subscription_cycle` invoice of the
same subscription and customer, with nothing paid. The gateway (`StripeGateway.void_invoice`)
turns Stripe's refusal into "return the invoice as it is", and transient errors into
`ProviderUnavailable` (503, Stripe redelivers). After a refusal the webhook checks the
returned invoice again. If it no longer qualifies (paid, partly paid), it is kept. If it
still qualifies, `VoidNotApplied` makes the endpoint answer 503 so Stripe redelivers. The
outcome string, an audit event and the new `cancellation_reason` column record what
happened. The billing page claims the void only when that audit event exists for the
subscription (`renewal_voided`).

**Senior/architectural.** The rule is derived from current state, not from one event type,
so it is order-independent and idempotent: any later event of that subscription re-checks
and finds the invoice `void`. It runs before the "followed subscription" check, so a delayed
cancellation of an earlier subscription still closes its own invoice without touching the
new one. Races with a customer's payment are resolved by Stripe (one of pay/void wins); the
code only reads the result. The trade-off: no reconciliation job, so if Stripe stops
redelivering, the invoice stays open until the next event; acceptable at beta volume.

**Questions and example answers.**

1. *Why not just set "mark uncollectible" in Stripe's Dashboard?* An uncollectible invoice
   can still be paid, and a Dashboard setting cannot be read through the API or tested in
   CI. The code rule is versioned, tested and scoped; the Dashboard stays as the owner set it.
2. *How do you avoid voiding the wrong invoice?* Five conditions: Stripe's own
   `payment_failed` cancellation, the subscription's latest invoice only, status `open`,
   `billing_reason=subscription_cycle`, same subscription and customer, `amount_paid == 0`;
   plus the existing tenant check. Each exclusion has a test (`test_paid_and_other_invoices_are_never_voided`).
3. *What if the customer pays at the same moment?* Stripe serialises operations on the
   invoice. If the payment wins, the void is refused; the gateway returns the paid invoice,
   the webhook re-checks it and keeps it, and a warning flags a possible refund. The page
   then does not claim a void. A refusal that leaves the invoice open and unpaid is *not*
   treated as an answer: it gives a 503 and a redelivery (a review found that the first
   version stored it as handled). Tested with a fake that pays during the void and through
   the real gateway with the SDK mocked; not reproducible on demand in the sandbox.
4. *What if Stripe's API fails mid-way?* `ProviderUnavailable` aborts the transaction, so
   neither the event nor the mirrored state is stored; the endpoint answers 503 and Stripe
   redelivers. Voiding twice is impossible because the retry sees `void`.
5. *Why keep a 7-day grace period when Stripe retries for 14?* It limits free use of a paid
   plan while a card fails. The customer sees both dates, and a successful retry restores
   the plan at once. Aligning them is a product decision left to the owner.
