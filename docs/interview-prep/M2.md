# Interview preparation: milestone 2 (bounded adaptive agent)

Honest framing: the agent, its tests and the evaluation were implemented with AI assistance
(Claude Code) to the owner's specification. It has been verified with a scripted test adapter
and a fake Ollama server, **not with a real model**. The scripted evaluation showed **no
advantage** over the deterministic baseline.

## Non-technical explanation

AccessGuard already knew how to run a fixed list of access tests. Milestone 2 lets an AI
assistant decide which test to run next, based on what earlier tests found. This could matter
when there is only time for some of the tests. The assistant is kept on a short leash:

- It can only pick a test from the approved list, or say "stop".
- It never sees passwords or customer data.
- It cannot invent new targets.
- It does not decide whether something is secure; the existing, rule-based engine does.

If the assistant fails, the report says so plainly and shows which tests did not run. So far
it has only been tried with a scripted stand-in, which did not beat the simple fixed order.

## Developer-level explanation

`AgentLoop` (`application/agent.py`) alternates between a model and the existing `CheckRunner`.

1. **Model view.** `ModelView` (`agent_view.py`) turns the approved check matrix into opaque
   aliases (`c001`, `a1`, `t1`, `r1`, ...). It renders a JSON state with enumerations only:
   kind, relation, expectation, outcome, finding type, HTTP status, session state and budget.
2. **Model call.** The model is called through the `ModelClient` port. The Ollama adapter
   POSTs to `/api/chat` on 127.0.0.1 with a JSON schema in `format`, `temperature` 0 and a
   fixed seed.
3. **Validation.** `parse_action` (`agent_contract.py`) accepts exactly
   `{"action":"run_check","check_id":...}` or `{"action":"stop"}`. It rejects:
   - oversized output, checked before parsing;
   - invalid JSON, `NaN`, duplicate keys, and extra or missing fields;
   - unknown actions and unknown ids;
   - repeats.

   Rejections are fixed categories, fed back in the next state.
4. **Execution.** A valid choice maps back to the immutable `Check`, which
   `CheckRunner.execute` judges exactly as in the baseline.
5. **Limits.** Model calls, invalid replies and output size are limited by `AgentLimits`.
   `RequestGate` enforces the HTTP budget (including probes, baselines and retests), the run
   deadline and the stop signal. `RequestGate.call_limit` applies the deadline and stop signal
   to every model call too.
6. **Reporting.** Failures end the loop with an `AgentStatus`; unexecuted checks become
   SKIPPED; the report (`run.agent`) records every step.

## Senior / architectural explanation

The design question was where to put the trust boundary for a component that is unreliable
and injectable by nature. The answer is to shrink what the model can express until every
expressible action is safe:

- **One tool.** Its only parameter is an alias from a server-generated allowlist.
- **No policy strings in prompts.** A policy id like `ignore-previous-instructions` is valid
  input, so the model sees only generated aliases.
- **Unchanged verdicts.** Verdicts stay in the M1 engine, so "same observation, same verdict"
  holds by construction. Tests verify it on four lab profiles.

The port keeps provider code out of the domain and the application. The Ollama client is
shared with the M1 reorder planner. Two consequences follow:

- Determinism and equality of budgets come from reusing one `RequestGate` for HTTP and model
  time.
- Honesty comes from explicit statuses, no fallback, SKIPPED for unselected checks, and
  `uses_ai: false` for the scripted adapter.

Evaluation is an architectural concern too:

- The order only matters under a budget, so strategies are compared at 25/50/100 % of a
  measured full budget.
- The fixtures are separate from the lab.
- Answer keys are read only after the runs.

The result, no advantage for the scripted heuristic, is reported as it is. The main known
trade-off: aliases also hide useful semantics from a real model.

## Five interview questions with example answers

1. **Why not let the model generate HTTP requests? That would be more powerful.**
   Power is the risk. A generated request could target metadata endpoints, other hosts, write
   methods, or carry credentials. Restricting the model to choosing an approved check means
   scope, endpoints, methods and credentials are not expressible at all. That is checked in
   `parse_action` and tested in `tests/security/test_agent_boundaries.py::ScopeExpansionTests`,
   not merely asked for in the prompt. The cost is that the agent cannot discover undeclared
   endpoints; that would need a separate, separately authorised tool.

2. **How do you stop prompt injection when the policy itself contains customer text?**
   The model never sees customer text. `ModelView` replaces every identifier, path, field name
   and description with generated aliases. Results are sent as enumerations and integers, never
   as reasons or response bodies. Tests build a policy whose ids read like instructions, and
   assert that none of them appear in any model request. Even if something got through, the
   contract would still only allow `run_check` with a pending alias, or `stop`.

3. **What happens when the model is slow, hangs or returns garbage?**
   - **Slow or hanging:** every call gets `RequestGate.call_limit`, which is the minimum of the
     per-call timeout and the remaining run time, plus the stop event. The transport reads in
     50 ms slices, so a hung or slow model is aborted, and Ctrl+C works mid-call
     (`test_in_flight_model_call_is_cancellable`).
   - **Garbage output:** it is rejected and counted. After `max_invalid_replies` the run ends
     with `invalid_replies_exhausted`.
   - **Provider errors:** these give `model_failed`.

   In every case, completed results are kept, the rest are SKIPPED, and the CLI exits with 5.
   There is never a silent switch to the deterministic order.

4. **How do you know the agent cannot change a verdict?**
   The model's only effect is which `Check` object `CheckRunner.execute` receives next. The
   check's expectation comes from the policy, not from the model. The verdict functions are the
   M1 ones. On the same scripted observations, `VerdictEquivalenceTests` compares every check's
   outcome, reason, finding type, evidence, verification and executed flag between the agent
   and a baseline run. `test_agent_lab.py` does the same over real HTTP on four lab profiles,
   comparing outcome, finding type, verification, executed flag and the overall status. All
   are identical, and the agent runs match the lab's hand-written ground truth.

5. **Did the agent help? How would you know?**
   Not in what was measured. On four synthetic fixtures under equal HTTP budgets, the scripted
   follow-up heuristic tied the deterministic order everywhere. A seeded random order found the
   first issue earlier, because the flaws sit late in policy order on those fixtures. The
   scripted adapter is not AI, so this validates the measurement, not a model. To claim a
   benefit I would:
   - run a real model, recording its digest and settings;
   - use more and more varied fixtures, including ones where flaws appear early;
   - report the variance across seeds and runs;
   - compare findings per request and requests to first finding against both baselines.

## Hands-on exercise

Make the agent stop early and inspect what the report says.

```powershell
$env:PYTHONPATH = "src;lab;evaluations"
py -3 -m accessguard_lab agent --profile vulnerable --model scripted:follow-up --max-requests 30 --out reports\exercise
```

1. Open `reports\exercise\vulnerable\report.json` and find `run.interrupted`,
   `run.agent.status`, `coverage.conclusive_ratio` and the SKIPPED results. Explain why the
   status is `findings` but `completed` is `false`, and why the findings are `not_retested`.
2. Count the requests used before the first FAIL (`requests_used_after`). Which part of that
   number is session probes and owner baselines?
3. In `tests/unit/test_agent_contract.py`, add a case for a reply with a trailing comment, such
   as `{"action":"stop"} // done`. Predict the rejection category before running
   `py -3 -m unittest tests.unit.test_agent_contract`.
