# Interview preparation: milestone 1

## Non-technical explanation

Software used by many companies must keep each company's data separate. AccessGuard logs in as
several test users from different companies and with different roles, tries to read each other's
data, and reports where the software lets someone see something they should not, with proof. It
also checks that data a company deliberately shared is still visible, so a "fix" that simply blocks
everything does not count as a success. It never says "secure"; it says which checks passed.

## Developer-level explanation

The customer writes a JSON policy: identities (tenant and role), resources with the fields that
prove disclosure, and explicit grants. `generate_checks` builds the full matrix of identities plus
anonymous against every resource and listing. `CheckRunner` first verifies every session via a
probe endpoint, then fetches each resource as its owner to establish a baseline, then requests it
as every other actor. `evaluate_item` and `evaluate_list` compare responses with the baseline:
all protected values present for a denied actor is FAIL, some is SUSPECTED, 403/404 is PASS, and
anything ambiguous (redirect, 429, 5xx, login page, invalid session) is INCONCLUSIVE. Failures are
retested. All network access goes through `ScopedHttpClient`, which only allows loopback addresses,
pins the connection to the validated IP and only sends GET. Reports are versioned JSON plus HTML.

## Senior / architectural explanation

The core risk of a security testing tool is false assurance, so the design optimizes for
"never green by accident": an explicit outcome taxonomy, an owner baseline as a precondition, a
session probe to prevent expired sessions from looking like denials, positive controls for
listings, retests, and an overall status that is green only when every planned check passed. The
second risk is the tool itself becoming dangerous (SSRF, credential leakage, destructive
requests), handled by a narrow outbound guard and minimal evidence. The structure is a layered
monolith with ports, so the HTTP transport, the planner (later an agent) and the report format can
change without touching verdict logic. The lab is a separate package with literal ground truth to
keep evaluation honest and keep deliberate flaws out of the product.

## Five interview questions with example answers

1. **Why not just flag any HTTP 200 for a cross-tenant request?**
   A 200 can be a login page, a soft error or an empty object. The engine requires the resource's
   protected values (established from the legitimate owner's response) to appear in the actor's
   response. A 200 without them is INCONCLUSIVE, not a leak and not a pass
   (`domain/evaluation.py`, `test_status_200_alone_is_neither_leak_nor_pass`). The same logic
   applies to denials: a 403 only counts as PASS when the body was actually read (parsed JSON or
   empty). An HTML or plain-text 403 page could contain the data, so it is INCONCLUSIVE
   (`BodyFormat`, `tests/unit/test_unanalysable_responses.py`).

2. **How do you prevent the tool from being used for SSRF or hitting cloud metadata?**
   The scope is a single origin. For every request the host is resolved again, every address must
   be loopback in M1, and the socket connects to the validated IP with the original Host header,
   which defeats DNS rebinding. Redirects are never followed and proxy variables are ignored
   (`adapters/http_target.py`, `tests/security/test_scope_enforcement.py`).

3. **Why the standard library instead of requests/httpx and pytest?**
   `http.client` lets me pin to a validated IP and guarantees no redirects or proxies; there are
   zero runtime dependencies, so the CLI runs offline with any Python ≥ 3.11. The trade-off is
   more hand-written code (transport, validation). unittest keeps tests runnable without
   installation; pytest would add value with more fixtures (ADR 0001, 0005).

4. **Why is a denied *granted* access a FAIL, when v0.1 called it inconclusive?**
   With a verified owner baseline and a verified session, a 403/404 for an actor the policy grants
   is a definite policy violation. Reporting it catches over-broad fixes that block legitimate
   sharing; requirements §10 explicitly reject such fixes (ADR 0002).

5. **Where does AI fit, and why is the default run not AI?**
   The model sits behind a `Planner` port and may only reorder approved checks; its output must be
   an exact permutation. It never sees credentials, cannot add targets and does not judge results.
   The deterministic baseline exists first so a future agent can be measured against it under the
   same budget. No real model has been run yet, which the README states.

## Hands-on exercise

Add a sixth lab flaw, `invoice-tenant-idor`, where `GET /invoices/{id}` skips the tenant check but
keeps the admin-role check.

1. Add the enum value in `lab/accessguard_lab/server.py` and use it in `_invoice`.
2. Before running anything, write the expected failing check ids by hand in
   `ground_truth.EXPECTED_FAILURES` (hint: which admins can now read which invoices?).
3. Run `py -3 -m accessguard_lab scan --profile invoice-tenant-idor` and inspect the report.
4. Run the test suite; `test_each_flaw_in_isolation` will now cover the new flaw.
5. Explain why members of other tenants still PASS for invoices, and which relation category the
   new findings appear under in `coverage.by_relation`.
